# 多账号并行与客户端服务端模式可行性分析

## 当前能力总结

- 当前项目以 CLI 和库调用为主，核心流程是每次 `Run` 调用处理一个 `Config` 和一个 `Filename`。
- OAuth 缓存路径和客户端密钥路径由进程级参数控制（`-cache`、`-secrets`），默认是单一文件（`request.token`、`client_secrets.json`）。
- 项目目前没有内置账号池调度器、没有用于账号登录管理的 Web 控制台，也没有内置并行上传任务队列。

## 结合目标场景的影响说明

目标场景示例：10 个账号，每个账号上传 6 个视频，总计 60 个视频并行处理。

- 当前版本无法直接以统一编排方式完成该场景。
- 现阶段可行的临时方案是人工启动多个独立进程，每个进程使用独立 token 缓存；但每个进程仍以单任务流程为主，运维复杂度较高。

## 推荐的架构演进路径

### 1）保留现有上传器作为底层执行单元

复用现有 `Run(ctx, transport, config, videoReader)`，作为服务端上传 Worker 的底层 API。

### 2）补齐账号隔离能力

- 引入显式 `AccountID` 和每账号独立 token 缓存路径。
- 在服务端场景中，减少对包级全局 flag 的隐式依赖。
- 为每个账号配置独立的限流和重试策略。

### 3）引入任务队列和调度器

- 任务模型建议：`{account_id, video_uri, metadata, priority}`。
- 调度策略建议包括：
  - 全局最大并发数。
  - 每账号最大并发数（安全起步可设为 1）。
  - 每账号每日配额保护。
- 队列实现可选 Redis、Postgres 或内存加持久化。

### 4）建设 Web 操作界面

- 账号绑定页面（OAuth 跳转授权流程）。
- 上传任务创建页面（支持批量添加视频）。
- 任务状态看板（排队、执行中、成功、失败）。
- 日志查询与失败重试控制。

### 5）实现客户端服务端模式

- 客户端负责采集媒体和元数据，并提交任务。
- 服务端负责 OAuth 身份管理与实际上传执行。
- 可选网络优化能力包括：
  - 基于内容分块的去重索引。
  - 传输前压缩。
  - 客户端到服务端分块断点续传。
  - 服务端近端对象存储暂存，减少重复跨广域网传输。

## 安全与合规建议

- 不传递、不存储账号原始密码。YouTube 上传应使用 OAuth 授权与 refresh token。
- 对 token 做静态加密存储，并限制最小访问权限。
- 记录审计日志，覆盖授权、上传动作、token 刷新等关键事件。

## 配额与异常提示建议

- YouTube Data API 默认每日配额是 10000 单位，配额按项目计费，不是按账号自动分配。
- 官方配额表显示：`videos.insert` 100、`thumbnails.set` 50、`captions.insert` 400、`playlistItems.insert` 50。批量任务需要按账号维度做预估与限流。
- 所有 API 请求（包括无效请求）都会消耗至少 1 个配额单位，因此要减少无效重试和参数错误。
- 当出现 `quotaExceeded`、`dailyLimitExceeded`、`uploadLimitExceeded` 等错误时，系统应实时提示用户并给出处理路径：
  - 进入 Google Cloud Console 的 Quotas 页面查看当日使用量。
  - 参考官方配额成本文档优化调用策略。
  - 在业务增长后通过官方 Audit and Quota Extension 流程申请扩容。
- 续传策略建议使用官方 resumable upload 协议，保留会话并在网络波动时继续分块上传，避免整文件重传造成额外失败与运维成本。

## 分阶段落地建议

1. 第一阶段：先完成服务端调度器和账号 token 隔离，不做 UI。
2. 第二阶段：补齐账号绑定和任务提交的基础 Web 页面。
3. 第三阶段：加入客户端服务端传输优化（去重、压缩、缓存）。
4. 第四阶段：加入配额感知的智能调度和成本分析能力。
